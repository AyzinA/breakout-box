# Breakout Box — v1.0.1 vs v1.0.2

This document compares **Breakout Box v1.0.1** with **Breakout Box v1.0.2** using the files included in the repository.

---

## Executive Summary

Version 1.0.1 was a compact OpenVPN-oriented breakout-routing script. It detected `tun0` and the Android WAN, enabled forwarding, created policy routes, inserted NAT/firewall rules, enabled ADB TCP, and watched for network changes.

Version 1.0.2 changes the module into a much more robust unattended service. It adds persistent configuration, self-healing health checks, worker supervision, dedicated iptables chains, rotating logs, runtime status, safer Android routing behavior, VPN-interface-generic routing, and a reusable secure HTTPS upgrader with multi-module manifest support.

For a phone expected to operate continuously as a breakout gateway, v1.0.2 is a major reliability and maintainability upgrade.

## 1. Module Metadata

### v1.0.1

```properties
id=breakout-box
name=Breakout Box
version=1.0.1
versionCode=1
author=NONAME
description=Adds breakout-box routing and NAT rules at boot
```

### v1.0.2

```properties
id=breakout-box
name=Breakout Box
version=1.0.2
versionCode=102
author=NONAME
description=Self-healing VPN breakout routing/NAT with secure HTTPS upgrader
```

### Difference

v1.0.2 uses a descriptive module summary that reflects the current self-healing service and HTTPS upgrader. It also moves from the original `versionCode=1` to `versionCode=102`.

## 2. Module Structure

### v1.0.1

```text
module.prop
service.sh
```

All module functionality lived in the service script.

### v1.0.2

```text
module.prop
service.sh
upgrader.sh
default-config.conf
customize.sh
uninstall.sh
```

The source repository additionally includes:

```text
README.md
CHANGELOG.md
update.json
update.json.example
docs/v1.0.1 vs v1.0.2.md
```

### Difference

v1.0.2 separates runtime logic, installation, configuration, cleanup, and upgrade functionality instead of placing nearly everything in `service.sh`.

## 3. VPN Interface Handling

### v1.0.1

The service is explicitly OpenVPN-oriented:

```sh
VPN="tun0"
VPN_NET="10.8.0.0/24"
```

State tracking is also based around `tun0` recreation and address changes.

### v1.0.2

The service reads configurable values:

```sh
VPN="${VPN_INTERFACE:-tun0}"
VPN_NET="${VPN_NETWORK:-10.8.0.0/24}"
```

The WAN detector explicitly excludes whatever interface is configured as the VPN interface rather than assuming every VPN device starts with `tun`.

This means the same routing engine can be configured for OpenVPN or another interface such as WireGuard `wg0`.

Example:

```sh
VPN_INTERFACE="wg0"
VPN_NETWORK="10.10.0.0/24"
```

### Difference

v1.0.1 is effectively tied to the OpenVPN `tun0` convention. v1.0.2 is VPN-interface-generic while retaining OpenVPN-compatible defaults.

---

## 4. Persistent Configuration

### v1.0.1

Settings are hardcoded inside `service.sh`, including:

```sh
VPN="tun0"
VPN_NET="10.8.0.0/24"
VPN_TABLE="100"
WAN_TABLE="101"
CHECK_INTERVAL="10"
ADB_PORT="5555"
```

Changing a setting requires editing the script.

### v1.0.2

Packaged defaults are stored in:

```text
default-config.conf
```

Persistent per-device settings are stored in:

```text
/data/adb/breakout-box/config.conf
```

`customize.sh` creates the persistent config when it does not exist and preserves an existing config during upgrades.

### Difference

v1.0.2 allows different devices to have different VPN subnets, interfaces, table IDs, timings, ADB settings, logging limits, and upgrader settings without changing `service.sh`.

---

## 5. Network Polling

### v1.0.1

```sh
CHECK_INTERVAL="10"
```

### v1.0.2

```sh
CHECK_INTERVAL_SECONDS="3"
```

### Difference

Network-state transitions can be noticed considerably faster in v1.0.2.

Typical events include:

- VPN reconnect.
- VPN interface recreation.
- VPN address change.
- Wi-Fi disconnect/reconnect.
- Mobile-data reconnect.
- Wi-Fi/mobile WAN switching.
- WAN gateway change.

---

## 6. Boot Handling

### v1.0.1

The service uses a fixed startup delay:

```sh
sleep 20
```

### v1.0.2

The service waits for Android's boot-completed state, with a bounded wait.

### Difference

v1.0.2 bases initialization on Android state rather than assuming that a fixed delay is always sufficient.

---

## 7. Policy Routing Priorities

### v1.0.1

The original service uses:

```text
9999
10000
10001
```

### v1.0.2

The defaults are:

```text
9000
9001
9002
```

and are configurable:

```sh
VPN_TO_CLIENT_PRIORITY="9000"
VPN_FROM_CLIENT_PRIORITY="9001"
VPN_IIF_PRIORITY="9002"
```

### Difference

v1.0.2 moves its rules earlier and keeps the values configurable, improving compatibility with Android networking policy rules.

---

## 8. WAN and Gateway Handling

### v1.0.1

The script detects the active WAN and contains a Wi-Fi gateway fallback. It then installs the custom WAN-table default route.

### v1.0.2

The logic is more explicit:

- Detect active WAN from `ip route get 8.8.8.8`.
- Ignore the configured VPN interface as a WAN candidate.
- Detect an explicit gateway when present.
- Apply the Wi-Fi `.1` fallback when Android omits a Wi-Fi gateway.
- Add a gateway host route to the custom WAN table before installing the default route.
- Fall back to an `onlink` default when required.
- Support direct defaults for cellular/point-to-point interfaces without a gateway.

### Difference

v1.0.2 is better suited to Android's per-network routing behavior and custom table `101`.

---

## 9. Firewall Management

### v1.0.1

The original service directly inserts rules into Android chains and scans a list of possible WAN interfaces when cleaning old rules.

It manipulates rules in locations such as:

```text
FORWARD
POSTROUTING
tetherctrl_nat_POSTROUTING
```

### v1.0.2

The module owns dedicated chains:

```text
BB_FORWARD
BB_NAT
```

and hooks them into:

```text
FORWARD
POSTROUTING
```

### Difference

Dedicated chains make ownership clearer, cleanup simpler, health checks easier, and updates less dependent on enumerating Android WAN interface names.

---

## 10. Conntrack Handling

### v1.0.1

After rebuilding NAT rules, the service attempts a global conntrack flush when `conntrack` is available:

```sh
conntrack -F
```

### v1.0.2

The global conntrack flush is removed.

### Difference

v1.0.2 avoids disrupting unrelated connections on the Android device merely because Breakout Box routing changed.

---

## 11. Self-Healing Health Checks

### v1.0.1

The main loop mostly reacts when tracked network state changes.

If an expected iptables or policy-routing rule disappears without an interface/gateway change, the service may not immediately detect it.

### v1.0.2

A full health check runs by default every:

```sh
HEALTH_CHECK_INTERVAL_SECONDS="15"
```

It verifies:

- IPv4 forwarding.
- VPN interface existence.
- VPN IPv4 address.
- WAN interface existence.
- Policy rules.
- Table `100` VPN route.
- Table `101` WAN default route.
- `BB_FORWARD` hook/rules.
- `BB_NAT` hook/MASQUERADE rule.

### Difference

v1.0.2 can repair state removed by Android `netd`, another root module, or another networking component even when the interfaces themselves did not change.

---

## 12. Repair Failure Handling and Supervisor

### v1.0.1

The service has one long-running main loop without a separate internal worker supervisor.

### v1.0.2

The routing logic runs as a worker under a supervisor.

Defaults:

```sh
MAX_REPAIR_FAILURES="3"
SERVICE_RESTART_DELAY_SECONDS="3"
```

Repeated repair failures cause the worker to return, after which the supervisor cleans policy state and restarts it.

### Difference

v1.0.2 has an additional recovery layer for failures that cannot be repaired inside one worker iteration.

---

## 13. Single-Instance Protection

### v1.0.1

No dedicated service lock directory is part of the original two-file module design.

### v1.0.2

The service uses:

```text
/data/adb/breakout-box/service.lock/
```

and records the owning PID.

If another live instance already owns the lock, the new instance exits instead of starting a second routing supervisor.

### Difference

v1.0.2 is safer against duplicate Magisk service execution.

---

## 14. ADB over TCP

### v1.0.1

ADB TCP is effectively built into the service with port:

```sh
ADB_PORT="5555"
```

### v1.0.2

It is configurable:

```sh
ENABLE_ADB_TCP=true
ADB_TCP_PORT="5555"
```

The service only restarts `adbd` when the configured values actually need to change.

### Difference

v1.0.2 can disable the feature entirely or choose another port without editing service logic.

---

## 15. Logging

### v1.0.1

The original release does not provide the current persistent structured file-log/rotation system.

### v1.0.2

Main service log:

```text
/data/adb/breakout-box/breakout-box.log
```

Defaults:

```sh
LOG_LEVEL="info"
MAX_LOG_SIZE=1048576
MAX_LOG_FILES=3
```

Rotations:

```text
breakout-box.log.1
breakout-box.log.2
breakout-box.log.3
```

The service also emits Android logcat messages using:

```text
breakout-box
```

### Difference

v1.0.2 provides persistent diagnostic history without allowing the active log to grow indefinitely.

---

## 16. Runtime Status

### v1.0.1

No equivalent persistent status-file system is part of the original release.

### v1.0.2

Main routing status:

```text
/data/adb/breakout-box/status
```

Upgrader status:

```text
/data/adb/breakout-box/upgrader.status
```

### Difference

Scripts and administrators can inspect recent state without requiring a live logcat session.

---

## 17. Upgrader

### v1.0.1

There is no `upgrader.sh` in the original module.

### v1.0.2

Adds a reusable secure HTTPS upgrader:

```text
upgrader.sh
```

It reads these values from the module's own `module.prop`:

```text
id
name
version
versionCode
```

It therefore does not need Breakout Box identity hardcoded into its core upgrade logic.

The manifest/ZIP hosting is also not GitHub-specific. Any accessible HTTPS server can be used through:

```sh
UPDATE_JSON_URL="https://example.com/update.json"
```

### Difference

v1.0.2 can check, validate, and install future module versions without requiring manual Magisk installation each time.

---

## 18. Multi-Module Manifest Support

### v1.0.1

Not applicable.

### v1.0.2

The preferred manifest can contain multiple module entries:

```json
{
  "schemaVersion": 2,
  "modules": {
    "breakout-box": {
      "version": "1.0.2",
      "versionCode": 102,
      "zipUrl": "https://example.com/breakout-box-v1.0.2.zip",
      "sha256": "..."
    },
    "another-module": {
      "version": "2.0.0",
      "versionCode": 200,
      "zipUrl": "https://example.com/another-module-v2.0.0.zip",
      "sha256": "..."
    }
  }
}
```

The local module selects the object matching its own `id=`.

The upgrader also remains backward compatible with the legacy root-level single-module format containing `moduleId`.

### Difference

One HTTPS manifest can now service multiple Magisk modules while each installed module checks only its own entry.

---

## 19. Upgrader Logging and Rotation

### v1.0.1

No upgrader exists.

### v1.0.2

Independent upgrader log:

```text
/data/adb/breakout-box/upgrader.log
```

Defaults:

```sh
UPGRADER_MAX_LOG_SIZE=1048576
UPGRADER_MAX_LOG_FILES=3
```

Android logcat tag:

```text
breakout-box-upgrader
```

Both service and upgrader output can be watched together:

```sh
adb logcat -s breakout-box:I breakout-box-upgrader:I
```

### Difference

Routing and upgrade operations have separate persistent logs while still being easy to observe in one logcat stream.

---

## 20. Update Security

### v1.0.1

No automatic update path exists.

### v1.0.2

The upgrader implements:

- HTTPS-only manifest URL validation.
- HTTPS-only ZIP URL validation.
- Optional mandatory SHA-256 verification.
- Numeric `versionCode` comparison.
- ZIP root `module.prop` extraction.
- Module-ID validation.
- ZIP `versionCode` validation.
- Temporary `.part` downloads before atomic rename.
- Upgrade-operation locking.
- Optional Wi-Fi-only checks.
- `AUTO_UPDATE=false` by default.

### Difference

The new automatic path is designed to reject malformed, mismatched, insecure, or unexpected upgrade artifacts before calling Magisk installation.

---

## 21. Android/Toybox Compatibility

### v1.0.1

The original service relies directly on the Android command environment.

### v1.0.2

The service uses an explicit Android/Magisk-friendly `PATH`, and the upgrader prefers Magisk/KernelSU BusyBox `awk` where available because vendor `awk` implementations can be unreliable on some ROMs.

The upgrader also provides fallbacks for downloading and SHA-256 calculation.

### Difference

v1.0.2 is more defensive across Android builds and root environments.

---

## 22. Upgrade Behavior

### v1.0.1

Updates are manual.

### v1.0.2

Automatic upgrades are optional and disabled by default:

```sh
AUTO_UPDATE=false
```

Manual check:

```sh
/data/adb/modules/breakout-box/upgrader.sh check
```

Status:

```sh
/data/adb/modules/breakout-box/upgrader.sh status
```

Automatic loop:

```sh
/data/adb/modules/breakout-box/upgrader.sh loop
```

After a verified ZIP is installed through Magisk, reboot is required.

---

## 23. Configuration Preservation

### v1.0.1

There is no separate persistent per-device configuration file.

### v1.0.2

`customize.sh` preserves:

```text
/data/adb/breakout-box/config.conf
```

when the module is upgraded.

### Difference

Device-specific settings survive module replacement, but new defaults introduced by later module versions may need to be manually merged into an older persistent config.

## 25. Bottom Line

v1.0.1 provides the essential breakout-routing concept in a compact script.

v1.0.2 keeps that routing model but makes it suitable for a more durable unattended deployment by adding persistent configuration, VPN-interface-generic behavior, dedicated firewall ownership, active health verification, recovery supervision, structured logging, and a reusable secure HTTPS upgrade system.
