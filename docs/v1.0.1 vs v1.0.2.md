# Breakout Box — Full Changelog and Comparison

## Version 1.0.1 vs Version 1.0.2

This document describes the architectural, functional, operational, and maintenance differences between **Breakout Box v1.0.1** and **Breakout Box v1.0.2**.

---

# 1. Executive Summary

Version 1.0.1 is a small, direct routing script. It detects the OpenVPN tunnel and active Android WAN, creates policy-routing rules, adds forwarding/NAT rules, and periodically watches for interface changes.

Version 1.0.2 turns Breakout Box into a more complete unattended service:

- Persistent per-device configuration
- Faster network-state detection
- Full self-healing health checks
- Worker supervision and restart
- Dedicated firewall chains
- Android-aware policy routing
- Safer Wi-Fi gateway handling
- Configurable ADB-over-TCP
- File logging and log rotation
- Status reporting
- Single-instance protection
- Universal secure GitHub upgrader
- SHA-256 verification
- Update ZIP validation
- Optional Wi-Fi-only updates
- Upgrade-safe configuration storage
- Uninstall support

For an Android phone acting as a **24/7 OpenVPN breakout gateway**, v1.0.2 is significantly more robust.

# 4. Configuration Architecture

## v1.0.1

Most settings are hardcoded directly inside `service.sh`.

Example:

```sh
VPN="tun0"
VPN_NET="10.8.0.0/24"

VPN_TABLE="100"
WAN_TABLE="101"

CHECK_INTERVAL="10"

ADB_PORT="5555"
```

Changing a setting requires editing the service script.

## v1.0.2

Settings are moved into:

```text
default-config.conf
```

On installation, the defaults are copied to:

```text
/data/adb/breakout-box/config.conf
```

The persistent file becomes the device-specific configuration.

Example:

```bash
VPN_INTERFACE="tun0"
VPN_NETWORK="10.8.0.0/24"

VPN_TABLE="100"
WAN_TABLE="101"

VPN_TO_CLIENT_PRIORITY="9000"
VPN_FROM_CLIENT_PRIORITY="9001"
VPN_IIF_PRIORITY="9002"

CHECK_INTERVAL_SECONDS="3"
HEALTH_CHECK_INTERVAL_SECONDS="15"

ENABLE_ADB_TCP=true
ADB_TCP_PORT="5555"

FILTER_CHAIN="BB_FORWARD"
NAT_CHAIN="BB_NAT"
```

### Configuration precedence

v1.0.2 effectively uses:

```text
built-in service defaults
        ↓
default-config.conf
        ↓
/data/adb/breakout-box/config.conf
```

The persistent config wins.

### Benefits

- Different phones can use different settings.
- No need to modify `service.sh`.
- Module upgrades do not need to overwrite per-device configuration.
- Easier deployment to many phones.

### Drawback

Persistent configuration needs migration logic when defaults change between releases.

# 5. Network Polling Speed

## v1.0.1

```sh
CHECK_INTERVAL="10"
```

Network state can take up to approximately ten seconds to be noticed.

## v1.0.2

```bash
CHECK_INTERVAL_SECONDS="3"
```

Network state is checked approximately every three seconds.

### Events detected faster

- Wi-Fi disconnect
- Wi-Fi reconnect
- Wi-Fi → mobile data
- Mobile data → Wi-Fi
- OpenVPN reconnect
- `tun0` recreation
- VPN address change
- WAN gateway change

### Benefit

Much quicker recovery when the phone changes connectivity.

### Cost

A few more lightweight shell/network queries per minute.

# 6. Self-Healing

## v1.0.1

The script mainly reapplies configuration when network state changes.

The watched values include:

- WAN interface
- WAN gateway
- `tun0` index
- `tun0` address

If an iptables rule disappears while all four values remain unchanged, the script may not notice.

## v1.0.2

A separate health check runs periodically:

```bash
HEALTH_CHECK_INTERVAL_SECONDS="15"
```

It verifies important runtime state even when the interfaces did not change.

The health checker covers:

- `net.ipv4.ip_forward`
- policy-routing rules
- VPN return route
- WAN routing table
- dedicated forwarding chain
- dedicated NAT chain
- forwarding rules
- MASQUERADE rule
- active VPN interface
- current WAN state

### Example

If another Android service flushes:

```text
BB_FORWARD
```

v1.0.2 can detect the missing chain/rules and recreate them.

### Benefit

This is one of the biggest improvements for unattended phones.

---

# 7. Worker Supervisor

## v1.0.1

There is one long-running loop.

Conceptually:

```text
service.sh
   └── while true
```

If the service process exits unexpectedly, there is no internal recovery mechanism.

## v1.0.2

The service is split conceptually into:

```text
service.sh
   |
   +-- supervisor
          |
          +-- service worker
```

The worker performs routing and health monitoring.

If repeated repairs fail, the worker exits and the supervisor starts a fresh worker.

Defaults:

```bash
MAX_REPAIR_FAILURES="3"
SERVICE_RESTART_DELAY_SECONDS="3"
```

Flow:

```text
health check fails
      ↓
repair attempt
      ↓
failure 1
      ↓
failure 2
      ↓
failure 3
      ↓
worker exits
      ↓
supervisor waits 3 seconds
      ↓
new worker starts
```

### Benefit

A temporary Android networking failure is less likely to leave the box permanently broken.

---

# 8. Android Boot Handling

## v1.0.1

Uses a fixed delay:

```sh
sleep 20
```

This assumes Android is sufficiently initialized after 20 seconds.

## v1.0.2

Uses Android boot state detection and waits for the system to become ready.

### Benefit

More reliable across:

- slower phones
- faster phones
- different Android versions
- different vendor ROMs

A fixed 20-second assumption is removed.

# 9. Android Command Compatibility

An early v1.0.2 test build used overly strict executable detection and could report:

```text
Missing required command: ip, iptables, awk, or grep
```

even though commands such as:

```sh
ip
iptables
awk
grep
```

worked interactively on Android.

This caused the service to exit before configuring the breakout box.

Symptoms were:

```text
ip_forward = 0
```

empty:

```text
table 100
table 101
```

and missing:

```text
BB_FORWARD
BB_NAT
```

The fixed v1.0.2 uses Android/Magisk-friendly command handling and an explicit PATH.

Example:

```sh
export PATH="/data/adb/magisk:/data/adb/magisk/bin:/system/bin:/system/xbin:/vendor/bin:/product/bin:$PATH"
```

### Benefit

Better compatibility with Android Toybox and Magisk environments.

---

# 10. Policy Routing Priority Change

## v1.0.1

Used:

```text
9999
10000
10001
```

Example:

```sh
ip rule add to "$VPN_NET" lookup "$VPN_TABLE" priority 9999
ip rule add from "$VPN_NET" lookup "$WAN_TABLE" priority 10000
ip rule add iif "$VPN" lookup "$WAN_TABLE" priority 10001
```

## Problem discovered on Android

The tested Android phone already had system policy rules beginning at priority:

```text
10000
10500
11000
12000
...
```

Therefore Breakout Box's priority `10000` could collide with Android's routing policy.

## v1.0.2

Defaults were changed to:

```bash
VPN_TO_CLIENT_PRIORITY="9000"
VPN_FROM_CLIENT_PRIORITY="9001"
VPN_IIF_PRIORITY="9002"
```

Result:

```text
9000  Breakout Box VPN return route
9001  Breakout Box VPN-source WAN route
9002  Breakout Box tun0 ingress WAN route
10000 Android/netd rules begin
...
```

### Benefit

Breakout Box routing is evaluated before the Android networking rules that were observed on the device.

### Possible downside

Another root networking module could theoretically also use the `9000` range.

For that reason the values are configurable in `config.conf`.

# 11. VPN Return Routing

Both versions use a dedicated VPN routing table.

Typical:

```text
table 100
```

The goal is to make traffic destined for the VPN subnet return through `tun0`.

Conceptually:

```text
destination 10.8.0.0/24
        ↓
table 100
        ↓
tun0
```

v1.0.2 adds health validation so a missing table/rule can be detected and restored.

---

# 12. WAN Policy Table

Both versions use a separate table, normally:

```text
101
```

for traffic received from VPN clients.

Conceptually:

```text
packet arrives from tun0
        ↓
policy rule
        ↓
table 101
        ↓
real Android WAN
```

The real WAN may be:

```text
wlan0
rmnet_data0
rmnet0
ccmni0
wwan0
...
```

---

# 13. Wi-Fi Gateway Handling

This is another major v1.0.2 improvement.

On the tested Android phone:

```text
8.8.8.8 via 10.0.1.1 dev wlan0 table wlan0 src 10.0.1.9
```

The active WAN was:

```text
wlan0
```

and gateway:

```text
10.0.1.1
```

## v1.0.1 behavior

The old design tries to create:

```sh
ip route replace default via 10.0.1.1 dev wlan0 table 101
```

On some Android versions this can fail because custom table 101 does not yet know how to reach `10.0.1.1`.

## v1.0.2 behavior

The new implementation first establishes gateway reachability in the custom table.

Conceptually:

```text
10.0.1.1/32 dev wlan0 scope link
default via 10.0.1.1 dev wlan0
```

If necessary it can use an `onlink` fallback.

### Benefit

More reliable policy routing on modern Android, where each physical network can have its own Android-managed routing table.

---

# 14. Mobile Data Handling

Mobile interfaces may not present a conventional gateway.

Example:

```text
rmnet_data0
```

may use:

```text
default dev rmnet_data0
```

rather than:

```text
default via X.X.X.X
```

v1.0.2 keeps support for both cases:

```text
Gateway exists
   -> default via GATEWAY dev WAN

No gateway
   -> default dev WAN
```

### Benefit

The same module remains usable with Wi-Fi and mobile data.

---

# 15. Firewall Architecture

## v1.0.1

Directly modifies shared Android chains such as:

```text
FORWARD
POSTROUTING
tetherctrl_nat_POSTROUTING
```

It also cleans rules by checking many possible interface names.

Example list includes interfaces such as:

```text
wlan0
swlan0
rmnet_data0
rmnet_data1
rmnet_data2
rmnet_data3
rmnet0
rmnet1
rmnet2
rmnet3
rmnet4
ccmni0
ccmni1
wwan0
usb0
```

## v1.0.2

Creates dedicated module-owned chains:

```text
BB_FORWARD
BB_NAT
```

and hooks them into the normal Android tables.

Conceptually:

```text
FORWARD
   ↓
BB_FORWARD
```

and:

```text
POSTROUTING
   ↓
BB_NAT
```

Typical forwarding rules:

```text
tun0 -> WAN     ACCEPT

WAN -> tun0     RELATED,ESTABLISHED
```

Typical NAT rule:

```text
10.8.0.0/24 -> WAN     MASQUERADE
```

### Benefits

- Easier troubleshooting
- Easier health checking
- Easier cleanup
- Less manipulation of unrelated firewall rules
- No need to enumerate every possible WAN interface during routine cleanup

---

# 16. Conntrack Behavior

## v1.0.1

Contains logic to globally flush conntrack:

```sh
conntrack -F
```

after network/routing changes when the command exists.

### Problem

That can remove connection tracking for unrelated Android applications.

Potentially affected connections include:

- Browser sessions
- RustDesk
- background applications
- other TCP connections
- other NAT state

## v1.0.2

Does not globally flush all conntrack state as part of normal reconfiguration.

### Benefit

Less disruption to Android's own network connections.

### Trade-off

A stale translated connection may survive temporarily across a WAN switch.

For general stability, avoiding a global flush is safer.

---

# 17. IPv4 Forwarding

## v1.0.1

Enables:

```text
/proc/sys/net/ipv4/ip_forward = 1
```

and interface forwarding/rp_filter settings during rule application.

## v1.0.2

Does the same but also health-checks forwarding state.

If something changes:

```text
ip_forward = 0
```

the health checker can detect and repair it.

### Benefit

Self-healing rather than one-time configuration.

---

# 18. Reverse Path Filtering

Both designs disable strict reverse path filtering for relevant Android interfaces.

This matters because the box deliberately uses asymmetric/policy routing:

```text
VPN client
   ↓
tun0
   ↓
Android WAN
```

and replies return through a different routing decision than Android's normal local application traffic.

v1.0.2 repeatedly ensures the required forwarding state remains valid.

---

# 19. ADB over TCP

## v1.0.1

ADB-over-TCP is always configured at startup.

Typical sequence:

```sh
setprop persist.adb.tcp.port 5555
setprop service.adb.tcp.port 5555

setprop ctl.restart adbd

sleep

stop adbd
sleep
start adbd
```

### Drawback

Even when ADB is already correctly configured, `adbd` can be unnecessarily restarted.

## v1.0.2

ADB is configurable:

```bash
ENABLE_ADB_TCP=true
ADB_TCP_PORT="5555"
```

It can be completely disabled:

```bash
ENABLE_ADB_TCP=false
```

The newer implementation avoids unnecessary restart work when possible.

### Benefits

- Fewer ADB interruptions
- Configurable port
- Can disable ADB behavior entirely
- Better for deployments where ADB is managed separately

# 20. Network State Detection

## v1.0.1

Uses multiple helper calls such as:

```text
get_wan
get_gateway
get_tun_index
get_tun_addr
```

## v1.0.2

Consolidates more of the network-state handling into:

```text
detect_network_state
network_state_changed
save_network_state
reset_network_state
```

### Benefit

Network information is managed more consistently and can be reused by health and repair logic.

# 21. Single-Instance Protection

## v1.0.1

Does not have explicit process locking.

It is therefore possible for more than one service instance to manipulate routing/firewall state if started manually or accidentally.

## v1.0.2

Uses locking to prevent duplicate workers/services from fighting over:

```text
ip rule
ip route
iptables
ADB
```

### Benefit

More deterministic state.

# 22. Runtime Status

## v1.0.1

No dedicated persistent status file.

## v1.0.2

Creates runtime status under:

```text
/data/adb/breakout-box/
```

This makes it easier to determine whether rules were applied or a repair failed.

Typical troubleshooting command:

```sh
cat /data/adb/breakout-box/status
```

### Benefit

Much easier remote diagnostics.

# 23. File Logging

v1.0.2 introduces persistent file logging.

Configuration:

```bash
LOG_LEVEL="info"
MAX_LOG_SIZE=1048576
MAX_LOG_FILES=3
```

The current log and rotated logs are retained in the module's state directory.

Typical layout:

```text
service.log
service.log.1
service.log.2
service.log.3
```

---

# 24. Log Rotation

v1.0.2 includes size-based rotation.

Default maximum log size:

```text
1,048,576 bytes
```

which is approximately:

```text
1 MiB
```

Number of rotated logs:

```text
3
```

The correct rotation order is:

```text
delete oldest .3
       ↓
move .2 -> .3
       ↓
move .1 -> .2
       ↓
move current -> .1
       ↓
create new current log
```

This avoids shifting the newly created `.1` twice.

### Approximate maximum storage

With:

```bash
MAX_LOG_SIZE=1048576
MAX_LOG_FILES=3
```

log storage is roughly:

```text
current        ~1 MiB
.1             ~1 MiB
.2             ~1 MiB
.3             ~1 MiB
---------------------
total          ~4 MiB
```

# 25. Universal Updater

v1.0.1 has no custom upgrader.

v1.0.2 includes:

```text
upgrader.sh
```

The upgrader is designed to be reusable across other Magisk modules.

It discovers the current module from:

```text
module.prop
```

rather than hardcoding:

```text
breakout-box
```

inside the upgrader.

---

# 26. Updater Configuration

The upgrader settings are stored in the same `default-config.conf`.

Default:

```bash
AUTO_UPDATE=false

UPDATE_CHECK_INTERVAL_SECONDS=86400
UPDATE_INITIAL_DELAY_SECONDS=120

UPDATE_JSON_URL="https://example.invalid/breakout-box/update.json"

UPDATE_REQUIRE_SHA256=true
UPDATE_INSTALL_ONLY_ON_WIFI=false
UPDATE_KEEP_DOWNLOADED_ZIP=false
```

## Current default behavior

```bash
AUTO_UPDATE=false
```

Therefore the automatic update loop is disabled.

This is intentional while the module is being tested.

Manual checks remain possible.

---

# 27. Update Loop Integration

`service.sh` contains update-loop startup logic.

Conceptually:

```sh
start_update_loop() {
    if bool_true "$AUTO_UPDATE"; then
        ...
        upgrader.sh loop
    fi
}
```

When:

```bash
AUTO_UPDATE=false
```

no upgrader loop is started.

When changed to:

```bash
AUTO_UPDATE=true
```

the upgrader can run periodically in the background.

---

# 28. Secure Update Process

The v1.0.2 upgrader uses this flow:

```text
read module.prop
       ↓
load update configuration
       ↓
download update.json over HTTPS
       ↓
read remote versionCode
       ↓
is remote newer?
       ↓ yes
download ZIP
       ↓
verify SHA-256
       ↓
extract ZIP module.prop
       ↓
verify module ID
       ↓
verify ZIP versionCode
       ↓
magisk --install-module
       ↓
reboot required
```

---

# 29. HTTPS Enforcement

The upgrader rejects non-HTTPS update URLs.

Allowed:

```text
https://github.com/...
https://raw.githubusercontent.com/...
```

Rejected:

```text
http://...
```

### Benefit

Reduces the risk of downloading updates over an unencrypted connection.

---

# 30. Partial Download Protection

Downloads are first written to a temporary file such as:

```text
module-update.zip.part
```

Only after the download completes successfully is it renamed to:

```text
module-update.zip
```

### Benefit

An interrupted download is less likely to be mistaken for a complete module package.

---

# 31. SHA-256 Verification

The update manifest can contain:

```json
{
  "sha256": "..."
}
```

When:

```bash
UPDATE_REQUIRE_SHA256=true
```

the downloaded ZIP must match the expected 64-character SHA-256 digest.

If it does not match:

```text
update rejected
```

### Benefit

Detects corrupted or unexpected downloaded ZIP files.

### Security note

SHA-256 is useful for integrity checking, but the hash is only as trustworthy as the update manifest that provides it. Protecting the GitHub account/repository remains important.

---

# 32. Module ID Validation

Before installation, the upgrader extracts:

```text
module.prop
```

from the downloaded ZIP.

Installed module:

```properties
id=breakout-box
```

If the ZIP contains:

```properties
id=android-exporter
```

the upgrader rejects it.

### Benefit

Prevents accidentally installing the wrong module through a bad `zipUrl`.

---

# 33. versionCode Validation

The upgrader verifies that:

```text
update.json versionCode
```

matches:

```text
downloaded ZIP module.prop versionCode
```

Example:

```text
update.json: 102
ZIP:         102
```

Accepted.

Example:

```text
update.json: 102
ZIP:         103
```

Rejected.

### Benefit

The downloaded artifact must correspond to the advertised release.

---

# 34. Optional Wi-Fi-Only Updating

Configuration:

```bash
UPDATE_INSTALL_ONLY_ON_WIFI=false
```

Can be changed to:

```bash
UPDATE_INSTALL_ONLY_ON_WIFI=true
```

Then automatic update checks/installations are skipped unless Android currently has a Wi-Fi route.

### Benefit

Useful if mobile-data consumption matters.

---

# 35. Update Polling Protection

Default:

```bash
UPDATE_CHECK_INTERVAL_SECONDS=86400
```

which is:

```text
24 hours
```

The upgrader also prevents accidentally using an excessively short polling loop.

### Benefit

Avoids hammering GitHub and unnecessary battery/network usage.

---

# 36. Initial Update Delay

Default:

```bash
UPDATE_INITIAL_DELAY_SECONDS=120
```

After boot, the upgrader waits approximately two minutes before its first automatic check.

### Benefit

Allows time for:

- Android boot
- network initialization
- OpenVPN
- Wi-Fi/mobile connectivity
- DNS

before contacting the update server.

---

# 37. Installer / Migration Logic

v1.0.2 includes:

```text
customize.sh
```

The installer can create:

```text
/data/adb/breakout-box/config.conf
```

from:

```text
default-config.conf
```

when the persistent file does not exist.

When the persistent config already exists, it can preserve per-device settings instead of replacing the entire file.

Migration is especially useful for routing-priority changes.

Example old defaults:

```text
9999
10000
10001
```

New defaults:

```text
9000
9001
9002
```

### Benefit

Existing installations can be upgraded without resetting every setting.

---

# 38. Uninstall Support

v1.0.1 does not contain a dedicated uninstall helper.

v1.0.2 contains:

```text
uninstall.sh
```

Its purpose is to remove module-owned runtime state such as routing/firewall artifacts when the module is removed.

### Recommended behavior

The uninstaller should preferably load:

```text
/data/adb/breakout-box/config.conf
```

before cleanup so that it removes the actual configured:

- policy priorities
- table numbers
- chain names

rather than assuming only the defaults.

# 41. v1.0.1 Advantages

Version 1.0.1 still has some legitimate strengths.

## Pros

### Simpler

Only two files and a relatively small service script.

### Easier to audit manually

The entire runtime behavior is easy to inspect in one file.

### Fewer moving parts

No:

- update daemon
- config migration
- log rotation
- supervisor
- dedicated status system

### Slightly lower background activity

Polling every ten seconds and no full health check means fewer shell commands.

### Good for temporary/manual use

If a phone is actively monitored and rarely changes state, the simpler design may be sufficient.

# 42. v1.0.1 Disadvantages

## Hardcoded configuration

Every phone effectively needs script modifications for custom behavior.

## Slower recovery

Up to roughly ten seconds to notice network changes.

## No full health checking

Missing routes/firewall state may remain broken when the network identity itself did not change.

## No worker supervisor

Unexpected service exit can leave the box offline.

## Android priority collision

Priority `10000` was observed to overlap Android's own policy-routing priorities.

## Weaker custom-table gateway handling

Wi-Fi gateway reachability in table 101 may fail on some Android versions.

## Direct firewall manipulation

Rules are inserted directly into shared chains rather than dedicated Breakout Box chains.

## Global conntrack flush

Potentially disrupts unrelated phone traffic.

## Unconditional ADB manipulation

Can restart `adbd` unnecessarily.

## Fixed boot delay

Assumes 20 seconds is enough for every device.

## No persistent configuration

Harder to maintain many phones.

## No structured logs

Troubleshooting is more difficult.

## No auto-update system

All updates are manual.

---

# 43. v1.0.2 Advantages

## Self-healing

Continuously verifies important runtime state.

## Faster failover

Three-second network monitoring.

## Supervisor recovery

Can restart the routing worker after repeated failures.

## Better Android routing compatibility

Uses configurable priorities before observed Android system rules.

## Better Wi-Fi gateway handling

Custom WAN table explicitly learns how to reach the physical gateway.

## Better mobile compatibility

Supports interfaces with and without explicit gateways.

## Cleaner firewall ownership

Dedicated:

```text
BB_FORWARD
BB_NAT
```

chains.

## Safer connection handling

Avoids global conntrack flushing.

## Configurable ADB

Can enable, disable, or change the ADB TCP port.

## Persistent per-device configuration

Settings survive module updates.

## Logging and rotation

Suitable for long-running unattended devices.

## Runtime status

Much easier remote troubleshooting.

## Universal update system

The same upgrader architecture can be shared with other Magisk modules.

## Update validation

Uses:

- HTTPS
- SHA-256
- module ID verification
- versionCode verification

## Auto-update disabled by default

Safe for testing:

```bash
AUTO_UPDATE=false
```

---

# 44. v1.0.2 Disadvantages

## More code

The system is much larger and requires more careful maintenance.

## More moving parts

Potential failures can occur in:

- service
- config
- installer
- upgrader
- log rotation
- migration
- supervisor

## Slightly more wakeups

Three-second monitoring plus periodic health checks performs more work than v1.0.1.

## Persistent-config migrations matter

Changing a future default does not automatically modify every existing device's `config.conf`.

## Policy-priority conflicts remain theoretically possible

Another custom root networking module could use `9000–9002`.

Because they are configurable, this can be corrected per device.

## Auto-update adds supply-chain responsibility

If later enabled, the GitHub repository becomes part of a privileged root update path.

The repository/account should therefore be strongly protected.

# 46. Expected v1.0.2 Runtime State

Assuming:

```text
VPN network: 10.8.0.0/24
VPN: tun0
WAN: wlan0
WAN IP: 10.0.1.9
Gateway: 10.0.1.1
```

expected policy rules are conceptually:

```text
9000: to 10.8.0.0/24 lookup 100
9001: from 10.8.0.0/24 lookup 101
9002: iif tun0 lookup 101
```

Table 100 should contain a VPN route similar to:

```text
10.8.0.0/24 dev tun0
```

Table 101 should contain something similar to:

```text
10.0.1.1 dev wlan0 scope link
default via 10.0.1.1 dev wlan0
```

Forwarding should be:

```text
1
```

from:

```sh
cat /proc/sys/net/ipv4/ip_forward
```

Firewall should contain:

```text
BB_FORWARD
BB_NAT
```

# 49. Self-Healing Tests

These tests are useful before deploying v1.0.2 widely.

## Test 1 — Forwarding repair

Temporarily set:

```sh
echo 0 > /proc/sys/net/ipv4/ip_forward
```

Wait for the health interval.

Then:

```sh
cat /proc/sys/net/ipv4/ip_forward
```

Expected:

```text
1
```

## Test 2 — Firewall chain repair

Delete or flush the module-owned forwarding chain/rules in a controlled test environment.

After the health interval:

```sh
iptables -L BB_FORWARD -n -v
```

The service should restore the required state.

## Test 3 — Wi-Fi to mobile

1. Start on Wi-Fi.
2. Confirm client internet.
3. Disable Wi-Fi.
4. Wait for mobile data.
5. Confirm table 101 changes to the mobile interface.
6. Confirm client internet resumes.

## Test 4 — Mobile to Wi-Fi

Reverse the previous test.

## Test 5 — OpenVPN reconnect

Disconnect/reconnect OpenVPN Connect.

Confirm:

```text
tun0
```

is rediscovered and rules are reapplied.

## Test 6 — Service worker recovery

Force the worker into a controlled failure and confirm the supervisor starts a new worker.

# 53. Upgrade Recommendation

For a production Android breakout box, **v1.0.2 is the recommended architecture**.

The largest reasons are not the upgrader itself.

The most important improvements are:

1. Android-compatible policy-routing priorities
2. Better custom-table gateway handling
3. Dedicated firewall chains
4. Full health monitoring
5. Automatic self-repair
6. Worker supervision
7. Faster WAN/VPN recovery
8. Persistent configuration
9. No global conntrack flush
10. Better diagnostics

The upgrader, logging, and configuration architecture then make the module easier to manage at scale.

# 55. Final Verdict

## v1.0.1

Best characteristic:

```text
simplicity
```

It is small and easy to understand.

Its weakness is that it assumes the Android routing/firewall state will remain mostly intact after initial configuration.

## v1.0.2

Best characteristic:

```text
resilience
```

It is designed for a rooted Android phone that should continue operating as a breakout gateway with minimal manual intervention.

The extra complexity is justified when the phone is expected to run continuously and automatically recover from:

- VPN reconnections
- Android network changes
- Wi-Fi/mobile switching
- deleted firewall state
- disabled forwarding
- transient service failures

For a 24/7 Breakout Box deployment, **v1.0.2 is the stronger long-term design**.
